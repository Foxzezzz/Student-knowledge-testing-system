# Правила работы с репозиторием

## Состав файлов

Отслеживаются исходники C#, XAML, файлы решений и проектов, тесты и Markdown. Исключаются `bin`, `obj`, настройки IDE, результаты тестов, временные файлы и локальные секреты. Правило `.gitignore` не убирает уже отслеженные файлы: для этого необходим `git rm --cached` после проверки пути. Полезные команды: `git status`, `git ls-files`, `git check-ignore -v путь`.

Не публиковать пароли, токены, закрытые ключи и секретные строки подключения. Если секрет попал в историю, необходимо отозвать/заменить его и оценить очистку истории и копий; простое удаление файла и `.gitignore` не устраняют утечку.

## Ветки и коммиты

`main` содержит объединённый результат. Каждый этап разрабатывается в собственной ветке `stage/NN-*`. Для моделирования команды в этапе 3 разрешены отдельные `feature/*`, объединяемые в ветку этапа. Перед слиянием проверяются изменения, сборка и тесты; после слияния - итоговая версия. Коммит должен быть небольшим и логически связанным, сообщение - кратким описанием результата на русском языке. Без изменения опубликованной истории и force-push, если не получено отдельное согласие.

## Учебный конфликт и контрольная точка

Учебный конфликт одной строки моделируется двумя независимыми правками в одной ветке: одна сохраняется в `git stash`, другая фиксируется коммитом, затем выполняется `git stash apply`. После появления маркеров конфликт разрешается вручную, результат добавляется и фиксируется. Это модель текстового конфликта, не свидетельство работы двух реальных участников. Последовательность и результат изложены в отчёте второго этапа. Контрольное состояние помечается тегом `stage-02-checkpoint`.

Историю можно изучить командой `git log --oneline --graph --decorate --all`.
